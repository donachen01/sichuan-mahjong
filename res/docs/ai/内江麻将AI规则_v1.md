# 内江麻将 AI 规则 v1

## 1. 文档定位

本文档用于固化当前内江麻将工程内 **实际生效** 的 AI 决策规则。

适用范围：

- 3 家电脑玩家的决策链
- 本家辅助建议链
- AI 调参面板中的中文说明与默认策略

维护约束：

- 后续凡是修改 AI 策略、调参项、阶段划分、攻守切换逻辑，都必须同步更新本文档。
- 本文档以当前工程的内江麻将实现为准，不再沿用四川麻将的定缺/花猪逻辑。
- **代码为准**：若本文档与当前代码存在差异，以代码为准，并立即回写本文档。
- **C# 为 AI 决策权威**：Godot 前端只构造合法候选、调度请求与执行结果，不得替 C# 选择弃牌、碰、杠、胡、报叫或报杠。

当前对应核心代码：

- `res://scripts/ai/csharp_ai_bridge.gd`：Godot 与 C# CLI / host JSON 传输桥
- `dotnet/AI.Core/Engines/NeijiangDecisionEngine.cs`：出牌主决策
- `dotnet/AI.Core/Engines/NeijiangExpectedScoreEngine.cs`：净分期望模型
- `dotnet/AI.Core/Engines/NeijiangSelfDrawProbabilityEngine.cs`：基于牌墙后验的自摸概率
- `dotnet/AI.Core/Engines/NeijiangRoutePlanEngine.cs`：牌型路线规划、路线权重、碰杠禁忌
- `dotnet/AI.Core/Engines/NeijiangReactionDecisionEngine.cs`：碰 / 杠 / 胡 / 过反应决策

## 2. 内江麻将基础前提

当前工程的内江麻将，基础约束如下：

- 只使用 **筒、条两门**
- 总牌数固定 **72 张**
- 无 **定缺**
- 无 **花猪**
- 第一轮发牌完成后，牌墙剩余 **19 张**
- 因牌墙更浅，内江节奏比四川麻将更短、更急

这 5 条前提会直接影响 AI 的：

- 巡目阶段划分
- 报叫/报杠决策
- 听牌速度权重
- 自摸率与点炮率估算
- 尾盘防守阈值

---

## 3. AI 总体目标

当前内江 AI 的目标，不是单纯“看到番就贪大”，而是尽量像熟练老玩家：

- 优先 **尽快成叫**
- 在同向听下优先 **宽叫、活张多、自摸率更高** 的路线
- 在两门浅牌墙环境下，更早进入 **防点炮 / 保查叫 / 保报叫权益**
- 有价值时可以追 `清一色`、`暗七对`、`龙七对`、`清对`、`清七对`、`青龙七对`
- 但不会为了贪大而明显拖慢听牌

当前总原则：

- **速度优先于空贪**
- **成叫优先于花活**
- **后期不点炮优先于追更大**

## 4. 当前决策链结构

### 4.0 前后端职责边界

当前工程采用“Godot 调度 + C# 决策”的模式：

- Godot 负责：
  - 维护牌局状态、动画、UI、反应队列、结算触发
  - 根据规则生成合法候选，例如 `canHu / canPeng / canGang / mandatoryGang`
  - 编码 `hand18 / visible18 / remaining18 / discards18 / melds18 / passedHu18 / passedPeng18 / passedGang18`
  - 执行 C# 返回的动作
- C# 负责：
  - AI 弃牌
  - AI 碰 / 杠 / 胡 / 过响应
  - AI 自摸 / 暗杠 / 补杠
  - AI 是否报叫、报哪些杠
  - 报叫后的必胡、必报杠、摸什么出什么
  - 地狱挑战透视与三家协作压制
- 禁止行为：
  - 前端不得把 C# 的碰改成杠
  - 前端不得在 C# 返回过牌时自行碰 / 杠
  - 前端不得替 C# 改弃牌
  - 若 C# 决策不合理，应修 C# 引擎、评分或输入参数，而不是在前端补丁覆盖

当前传输模式：

- 优先通过 Godot 内嵌 C# runtime 或 TCP host 请求
- host 不可用时可回退 CLI JSON
- 移动端可要求 `compactResult`，但不能改变决策语义

### 4.1 出牌主链

每张候选弃牌会综合以下维度评分：

- 向听速度：越接近 `0 向听` 越优先
- 进张数量：活张越多越优先
- 听口质量：`宽叫 > 两面 > 坎张/边张 > 单吊`
- 胡牌概率：结合剩余可见牌、后验分布、尾盘风险估算
- 番型价值：保留高价值路线，但不凌驾于成叫速度
- 结构稳定：孤张、废搭、断裂结构会被减分
- 防守风险：尾盘和高压局会显著抬权
- 自摸潜力：优先保留更容易自摸到的叫口
- 内江专项：两门牌压缩、报叫约束、卡二条收益、查叫收益

最终原则：

- 先比 **向听数**
- 向听相同再比 **进张 / 听口 / 胡率**
- 仍相同再比 **番型价值 / 风险**

当前 C# 出牌返回的关键诊断字段：

- `shanten / ukeire / liveUkeire`
- `waitCount / waitQualityScore / waitShapeLabel`
- `tenpaiProbability / selfDrawProbability / winProbability / dealInProbability`
- `expectedNetScore / expectedWinGain / expectedDealInLoss / expectedDrawRiskLoss / expectedReadyValue`
- `routePlan.primaryRoute / routePlan.secondaryRoutes / routePlan.routeWeights / routePlan.constraints / routePlan.reasons`
- 候选级 `routePlanPrimary / routePlanScore`
- `routesAfter / routeLoss`
- `candidateScores / reasons`

### 4.2 反应链

只处理：

- 胡
- 碰
- 杠
- 过

基本原则：

- 可胡时直接胡
- 碰牌必须带来 **成叫提速** 或 **明显的结构增益**
- 杠牌必须满足 **收益 > 风险**
- 牌墙浅时，`过` 的价值会比四川麻将更高
- 若同一张弃牌同时可碰可杠，最终仍由 C# 评分决定；前端不得把 C# 的“碰”擅自升级成“杠”。
- 当前 C# 已修正“碰后首打同张”的低级路线：若碰牌后最优弃牌仍是刚碰的同张牌，该碰会被判为无效副露并大幅降权，让明杠在这种场景自然胜出；若杠会明显拆坏牌型、碰能更快下叫，则仍允许 C# 选择碰。

### 4.3 杠牌链

分为：

- 暗杠
- 补杠
- 明杠

当前原则：

- 暗杠只要不破坏成叫速度，优先考虑
- 补杠重点防 `抢杠胡` 与尾盘放大风险
- 明杠不是“能杠就杠”，必须看当前是否逼近成叫、是否放大后验危险度
- 报叫后只允许杠 **报杠白名单** 内、且 **不破坏原有听型** 的牌

### 4.4 报叫专线

报叫玩家进入 C# `NeijiangBaoJiaoActionEngine` 专线：

- 自摸必胡
- 点炮必胡
- 摸到报杠白名单牌必杠
- 遇到报杠白名单弃牌必杠
- 非胡、非报杠响应只能过
- 自己摸牌后只能打本轮摸牌，即“摸什么出什么”
- 报叫后不能碰，不能临时新增报杠，不能改变听牌结构

AI 是否开局报叫，由 C# `NeijiangBaoJiaoDecisionEngine` 结合以下因素评分：

- 听牌门数
- 活张总数
- 报杠候选数量与类型
- 报叫计划基础分
- 当前牌墙剩余

当前阈值按牌墙剩余动态变化：

- 牌墙 `<= 8`：报叫阈值最低
- 牌墙 `<= 12`：中低阈值
- 牌墙 `<= 18`：中高阈值
- 更早阶段：高阈值，避免弱报叫

## 5. 阶段划分

内江麻将起手发完牌后只剩 19 张牌墙，因此阶段划分比四川麻将更短。

当前采用的阶段认知：

- 前期：0–5 弃牌
- 中期：6–11 弃牌
- 后期：12+ 弃牌

配套理解：

- 前期：优先整理结构、尽快逼近成叫
- 中期：开始严格比较宽叫、自摸率、报叫收益
- 后期：优先级切换为 **不点炮 / 保查叫 / 保报叫权益**

## 5.5 难度预设

当前难度配置以 `scripts/core/ai_tuning_config.gd` 为准，主要预设为：

- `intermediate`：中级
- `bone_ash`：骨灰级，当前默认难度
- `hell`：地狱挑战

### 5.5.1 中级

中级用于保留可玩性和容错：

- 前瞻候选较少：`lookahead_candidate_count = 2`
- 摸牌抽样较少：`lookahead_draw_samples = 5`
- 杠牌门槛更高：补杠 `18`，暗杠 `28`
- 允许从前几名候选中选择：`intermediate_top_pick_count = 3`
- 攻击倾向低，防守倾向较高
- 仍重视快速下叫和自摸，但读牌强度弱于骨灰级

### 5.5.2 骨灰级

骨灰级是当前默认实战 AI：

- 前瞻候选：`4`
- 摸牌抽样：`8`
- 补杠门槛：`10`
- 暗杠门槛：`18`
- 候选选择更集中：`intermediate_top_pick_count = 2`
- 攻守均衡偏强
- 快速下叫、自摸、读牌、尾盘绝对防守均开启
- 不使用透视，不读取本家暗手或精确牌墙

### 5.5.3 地狱挑战

地狱挑战是独立难度，不代表公平 AI：

- 前瞻候选：`5`
- 摸牌抽样：`12`
- 补杠门槛：`8`
- 暗杠门槛：`16`
- 候选选择固定最优：`intermediate_top_pick_count = 1`
- 三家 AI 共享 AI 手牌
- 可读取本家手牌
- 可读取精确牌墙
- 可执行 oracle 动作
- 开启三家 AI 团队协作压制本家

地狱挑战的设计目标不是“正常人类公平水平”，而是用于压力测试和高压体验。它可以主动压制本家，但仍应保留真实麻将互动：只要不点炮、不严重放大本家胡牌，不能把所有本家可碰牌都绝对封死。

## 6. 局势判断规则

### 6.1 两门牌桌面判断

内江麻将没有定缺格局判断，改为识别 **两门浓度与竞争压力**：

- `单门偏重`
  - 自己某一门明显更集中
  - 可以更积极评估 `清一色` 或半染路线
- `双门均衡`
  - 两门分布接近
  - 更偏向保留宽叫与进张弹性
- `高压浅墙`
  - 牌墙低、他家副露多、有人报叫
  - 优先保命、防点炮、保成叫

### 6.2 手牌类型判断

当前仍保留 4 类粗分：

- `进攻型`
  - 对子较多、连张较多、成型快
- `均衡型`
  - 有基础搭子，攻守都能转
- `防守型`
  - 成型一般，但可保守推进
- `摆烂型`
  - 孤张多、废搭多、结构散

### 6.3 对手画像判断

AI 当前读取的主要信号：

- `fast_call_count`
  - 副露频繁、明显抢速度的对手数量
- `silent_big_hand_count`
  - 长时间不碰不杠，疑似憋大牌的对手数量
- `flush_watch_count`
  - 疑似清一色的对手数量
- `pung_watch_count`
  - 疑似对对胡/将对路线的对手数量
- `top_threat_profile`
  - 当前最危险对手及其危险花色

## 7. 内江高手规则落地

### 7.1 快速成叫第一优先

AI 每次出牌前，会遍历所有可打牌，模拟打出后重新计算：

- 向听数
- 可听牌面
- 活张数量
- 胡牌概率

当前基本决策顺序：

1. 先选 **向听数最小**
2. 若同向听，选 **进张更多**
3. 若同进张，选 **宽叫更优**
4. 若同宽度，选 **自摸率更高 / 活张更多**
5. 若仍接近，再看 **净分期望**
6. 净分接近时，再看番型路线与风险解释

当前已接入额外强约束：

- 前中期若某候选能直接下叫，且听口不是极窄，速度分会压过普通大牌路线保留。
- 大牌路线仍可保留，但不能在明显慢于平胡下叫时硬保对子或刻子。
- 同向听时不再给七对/大对子路线硬排序特权；路线只通过 `routePlanScore / expectedNetScore / reasons` 进入总分，若总分明显落后或风险明显更高，必须让位给更稳、更快的候选。
- 若拆对子 / 拆刻子能立刻成叫，C# 会给“能下叫先下叫”的正向理由，而不是死守大牌形。

### 7.1.1 净分期望模型

当前出牌主链已经不再只使用“经验分”排序，而是为每一张候选弃牌计算：

- `预期胡牌收益`
  - 估算当前候选路线的基础番档
  - 按 `1番=1分、2番=2分、3番=4分、4番=8分、5番=16分` 折算
  - 自摸按“每家支付胡牌分 + 自摸额外 1 分”估算
- `预期点炮损失`
  - 使用对手听牌后验、胡这张后验、危险度估算对手番档
  - 按候选弃牌的点炮概率折算损失
- `查叫 / 报叫残局风险`
  - 如果候选牌导致未成叫或成叫概率低，后期按牌墙剩余、对手听牌后验估算查叫赔付风险
- `成叫价值`
  - 0 向听、宽叫、活张多、牌墙后验高，会形成正向补偿

简化表达：

`净分期望 = 预期胡牌收益 - 预期点炮损失 - 查叫风险 + 成叫价值`

### 7.1.2 当前权重量级与同尺比较

当前 C# 出牌链采用“候选综合分”排序。除少数尾盘硬防守 override 外，路线、速度、番值、防守、点炮风险都必须回到同一把尺子上比较。

综合分口径：

- `expectedValue = expectedScore.Net + shapeValue - defenseAdjustment`
- `score = round(expectedValue * 100)`
- `expectedScore.Net` 来自净分期望模型
- `shapeValue` 包含手形、听形、前瞻、快速下叫、路线规划、大牌路线、孤张/中张骨架、保对子/刻子等调整
- `defenseAdjustment` 来自点炮概率、后验压力、牌墙阶段、是否已下叫、听口宽度等防守修正

路线规划量级：

- `RoutePlan` 本身先输出 0-100 的路线权重，只用于判断主路线、副路线和约束。
- 候选出牌时，`EvaluateRoutePlanAdjustment` 返回 double，再乘 `100` 合入候选总分。
- 七对主路线下拆对子通常约 `-20.0 * 100 = -2000`。
- 七对主路线下拆刻子/三张通常约 `-28.0 * 100 = -2800`。
- 若弃牌后能直接下叫，七对拆对子/拆刻子的惩罚会按 `speedScale = 0.20` 缩小，即约 `-400` 到 `-560`；同时会获得“能下叫先下叫”的速度加分。
- 因此七对要保护，但不能压过明确成叫；能下叫时允许退出七对或切到平胡路线。
- 清一色路线下，异门未清完而拆目标花色通常约 `-11.0 * 100 = -1100`；若单门已经 `10+` 且异门 `<=3`，拆目标花色提高到约 `-24.0 * 100 = -2400`。
- 清一色路线下清理异门通常约 `+1000` 到 `+1800`；若已经形成强清色胚子，再额外加约 `+800`。这用于修复“明明该做清一色却先打本门牌”的问题。
- 四张同牌属于 `归 / 杠材 / 高番资源`。打一张虽仍剩刻子，但会失去归与杠材潜力，前中期约 `-18.0 * 100 = -1800`，后期约 `-12.0 * 100 = -1200`；不能再按普通刻子轻拆处理。
- 大对子/清对路线下，未成叫前拆刻子约 `-1500`，拆对子约 `-800`。
- 平胡路线下，能保持速度和宽叫会有小幅正分；它不靠番型硬加权，而靠下叫速度、活张和净分期望取胜。

快速下叫量级：

- 候选能直接下叫且有听口时，基础速度加分约 `+800` 到 `+1500`，再按听口数量和活张补正。
- 候选只是降向听时，加分约 `+350` 到 `+700`。
- 高危牌在中后期会削弱速度加成，避免“为了下叫直接点炮”。
- 这套分值故意能覆盖普通路线保护，避免 AI 为了做七对/大对子错过现实下叫。

防守与点炮量级：

- 点炮风险先经 `NeijiangRiskCalibration.ToDealInProbability` 转成概率，再进入 `expectedScore.DealInLoss`。
- 对手后验越高、危险度越高、越到后期，`dealInProbability` 越高；当前上限约 `0.54`。
- `EstimatePosteriorDefensePenalty` 会额外惩罚高后验、高点炮率、后期未成叫、活张少的候选。
- `ResolveDefenseAdjustmentWeight` 会把后验防守惩罚按阶段放大：中期更重，后期更重，未听更重，窄听更重。
- 极危同速情况下，`SelectExtremeDangerSameSpeedOverride` 会在不降低速度和听口的前提下选更安全候选。
- 牌墙极少时，`SelectLateWallDefenseOverride` 会优先选同速更安全牌；但如果当前已经成叫，不会随便为了安全拆掉下叫。

排序层硬约束：

- 当前已取消七对/大对子在同向听下的硬排序特权。
- `RoutePlan` 内部若多条路线同分，优先保留更明确的大牌路线诊断，例如强清色、清七对、青龙七对；但候选弃牌最终仍只按综合分排序。
- 路线只能通过 `routePlanScore / expectedNetScore / reasons` 进入总分。
- 若大牌路线候选总分明显落后、危险明显更高或活张明显更差，必须让位给更快下叫、更低点炮风险的普通候选。
- 回归测试 `SmokeBigPairRouteDoesNotOverrideLargeScoreGap` 固化该约束：同向听时，`Score=1000 / Danger=74` 的七对路线不能压过 `Score=3200 / Danger=18` 的普通候选。
- 回归测试 `SmokePotentialFlushPrefersOffSuitDiscard` 固化清一色潜力识别：单门 `11` 张、异门 `3` 张的强清色胚子，主路线必须进入清一色，并优先清理异门。
- 回归测试 `SmokeQuadTileGetsStrongPreservationPenalty` 固化四张同牌保护：四张同牌打一张不能再是 `0` 惩罚，必须给出“归牌/四张同牌不轻拆”的强降权理由。

落地代码：

- `dotnet/AI.Core/Engines/NeijiangExpectedScoreEngine.cs`
- `dotnet/AI.Core/Models/NeijiangExpectedScore.cs`
- `dotnet/AI.Core/Models/NeijiangCandidateDetail.cs`
- `dotnet/AI.Core/Engines/NeijiangDecisionEngine.cs`
- `dotnet/AI.Core.Smoke/Program.cs`

候选输出字段：

- `expectedNetScore`
- `expectedWinGain`
- `expectedDealInLoss`
- `expectedDrawRiskLoss`
- `expectedReadyValue`

### 7.2 宽叫优先

当前明确执行：

- `宽叫 > 两面 > 坎张/边张 > 单吊`
- `听必现张` 优于普通听张
- `听剩张多` 优于听剩张少

### 7.3 自摸优先

两门浅牌墙下，AI 更偏好保留：

- 对手不容易先碰走的张
- 剩余数量更多的张
- 后验上更可能还在牌墙中的张

即：

- `活张多` 更优
- `牌墙后验更高` 更优
- `多面同时可自摸` 更优

当前自摸率不再使用简单线性经验公式，而是按以下近似计算：

1. 统计候选弃牌后的所有可胡 / 可进张听口
2. 对每个听口读取：
   - 当前剩余张数
   - `牌墙后验`
   - 当前牌墙剩余数量
3. 估算自己在剩余牌墙中的可摸次数：
   - 未胡玩家越少，自己可摸机会越多
   - 1 向听、2 向听会按距离听牌的远近折减
4. 使用 `1 - (1 - 单次摸中概率) ^ 可摸次数` 计算“至少摸中一次”的概率
5. 再用宽叫数量、活张数量、危险度做小幅修正

落地代码：

- `dotnet/AI.Core/Engines/NeijiangSelfDrawProbabilityEngine.cs`

这条规则的含义是：AI 不只看“胡张有几张”，还会看“这些张更可能在牌墙里，还是更可能被别人捏在手里”。

### 7.4 卡二条优先

若 `卡二条` 成立且不明显拖慢速度：

- 会提高其保留权重
- 在报叫收益评估中额外加分
- 在同分路线中可作为优先保留项

### 7.5 碰牌规则

当前碰牌改为“老手主动抢听”风格：不是乱碰，但在不拖慢成叫时会明显更积极。

优先碰的情况：

- 碰后直接成叫
- 碰后从 2 向听压到 1 向听
- 碰后不升向听，且活张不比原路线明显少
- 对子较多、七对路线不稳，碰后可减少对子冗余
- 前中盘碰后能定型抢听，首打风险未达到明显高危

明确不鼓励的情况：

- 碰后升向听
- 碰后听口变窄
- 碰后尾盘防守能力显著下降
- 多家高后验听牌且碰后仍未成叫
- 当前已经能同张明杠时，若 C# 估算碰后首打仍是这张牌，会把该碰判为无效副露并大幅降权。
- 七对类路线成立时，碰牌会破坏七对，不能为了普通碰牌收益破坏七对主线。

当前碰牌权重量级：

- 碰后直接成叫、降向听、活张不亏，会获得主要进攻加分。
- 碰后仍同向听但活张接近，且能主动定型抢胡，会有中等加分。
- 碰后不降向听、活张不增、结构收益不足，会降权。
- 碰后第一打危险度高会降权；尾盘或对手后验压力高时，非必要不碰。
- 碰后最优首打仍是被碰的同张，扣约 `-640`；若手里已有三张、同张本可明杠，再额外扣约 `-980`。
- 七对已听扣约 `-1320`；当前 `RoutePlan` 明确禁止碰时扣约 `-6000`。
- 这表示“碰牌可以抢听”，但不能为了碰牌把自己拖慢，也不能出现碰完又打同张的低级路线。

### 7.6 杠牌规则

当前杠牌链重点关注：

- 杠后是否仍保持成叫速度
- 是否触发抢杠胡风险
- 是否会在浅牌墙尾盘放大点炮风险
- 报叫后是否属于合法报杠白名单

本轮后杠牌权重改为更贴近内江“雨钱收益”：

- 暗杠 / 补杠 / 明杠的税收益进入 C# 评分
- 杠后不升向听、活张不差、首打风险可控时，明显提高执行倾向
- 杠后已经成叫，或杠后仍保持 0 向听，会更积极收雨钱
- 只有在杠后拖慢成叫、尾盘未叫、或后验风险明显高时才强降权
- 七对类路线下，任何杠都会破坏七对；因此暗七对、龙七对、清七对、青龙七对路线不能暗杠、明杠或补杠。
- 报叫后只有报杠白名单内的杠可以执行，且由 C# 报叫专线最终确认。

当前杠牌权重量级：

- 明杠有雨钱收益和补牌收益，基础倾向高于普通碰，但仍必须比较杠后向听、活张和首打风险。
- 暗杠/补杠会看杠后是否不拖慢成叫；杠后仍下叫会明显加分。
- 杠后向听变差、活张明显减少、首打风险高，会降权。
- 补杠若存在抢杠胡候选，会按可抢杠人数强降权。
- 补杠后仍未成叫，尤其在中后期，会继续降权。
- 当前 `RoutePlan` 明确禁止杠时扣约 `-6000`，覆盖暗杠、明杠、补杠。
- 因此“能杠”不等于“必须杠”；杠必须同时满足收益、速度和安全性。

### 7.7 报叫规则

当前内江规则要求：

- 仅闲家支持开局报叫
- 发牌结束后手牌直接听牌，才允许报叫
- 报叫 +1 番
- 报叫后手牌锁定，不可换牌、不可碰牌
- 若报叫同时有合法报杠，则只允许杠报杠白名单中的牌

AI 当前在报叫决策中重点看：

- 听牌张数
- 活张总量
- 是否含 `卡二条`
- 查叫收益
- 是否保留报杠白名单

报叫后动作规则：

- 自摸必胡
- 点炮必胡
- 摸到报杠白名单牌必杠
- 遇到报杠白名单弃牌必杠
- 非胡、非报杠只能过
- 本轮摸牌后只能打摸入牌

这些规则均落在 C# 报叫专线；前端不得在报叫后自行选择其他手牌或替 C# 改动作。

报杠选择界面当前口径：

- Godot 只展示 C# / 规则候选给出的合法报杠项，不自行增加候选。
- 人类玩家选择报杠时，只显示一个桌面风格面板；右上角 `X` 用于完成并关闭，不再显示底部“确认 / 取消”按钮。
- 候选报杠牌从左到右横排展示，最多 4 张，直接用麻将牌面而不是文字列表。
- 候选默认选中，点牌可切换选中状态；关闭时把选中的 `bao_gang_keys` 写回状态，后续只能杠这些白名单牌。
- 本家与 AI 的报杠牌都会在各自手牌区按 `bao_gang_tiles` 单独框出，方便玩家看到哪些牌已经声明。

### 7.8 当前番型路线认知

当前 C# 已接入独立 `NeijiangRoutePlanEngine`。它不是开局锁死的死路线，而是在每次出牌、碰杠响应、自摸/暗杠/补杠评估前按当前手牌轻量重评，输出主路线、副路线、路线权重、约束和原因。

当前路线集合：

- `平胡`
- `卡二条平胡`
- `暗七对`
- `龙七对`
- `清七对`
- `青龙七对`
- `大对子`
- `清对`
- `清一色`

当前路线权重来源：

- 标准牌型向听与活进张
- 七对向听、对子数量、刻子/归潜力
- 同门牌数量、异门牌数量、目标花色
- 顺子搭子、两面搭子、坎边张结构
- 当前副露数量与是否仍可做门清七对
- 结算层已有番值：平胡、卡二条、暗七对、龙七对、清七对、青龙七对、大对子、清对、清一色

当前净分期望会把路线折算为估番：

- 清一色、七对、对对胡基础按高番路线估算
- 清一色 + 七对、清一色 + 对对胡按 4 番路线估算
- 存在归潜力时追加番值潜力
- 最终估番限制在 1 到 5 番之间

清一色路线当前细化：

- `TargetSuitCount >= 11 && OffSuitCount <= 3`：强清色胚子，清一色权重显著提高。
- `TargetSuitCount >= 10 && OffSuitCount <= 3`：清一色主线候选，优先清异门。
- `TargetSuitCount 8-9`：清一色副线，只能在不拖慢成叫、不增加点炮风险时保留。
- 候选出牌后的 `EstimateRoutes` 也会识别强清色胚子，把它纳入番值期望，而不是等到完全清一色才算清一色价值。
- 若清色路线和直接下叫冲突，仍按综合分比较；直接下叫、宽叫与低风险可以压过伪清色。

当前路线约束已经接入：

- 七对系主线包含 `forbid_melds / forbid_gangs / preserve_pairs`，即禁止碰、明杠、暗杠、补杠。
- 七对系原因会明确写出“碰杠会破坏七对”。
- 清一色系主线包含目标花色约束，优先清理异门，但不能为了伪清一色错过直接下叫。
- 四张同牌作为归 / 杠材资源被单独保护。除非综合分证明它能立刻带来更好的下叫、胡牌收益或低风险，否则 AI 不应把四张同牌当普通刻子随手拆。
- 大对子 / 清对会保留对子、刻子价值，但若平胡能明显更快下叫，不会硬守对子。
- 三对子默认不死做七对，优先平胡抢听；五对子及以上才强推七对/龙七对/清七对路线。
- 同一弃牌同时可碰可杠时，前端不得改结果；C# 会在响应评分中比较碰后速度、杠后收益、是否破坏当前路线。

当前仍保留的长期优化方向：

- 路线记忆目前是“每次轻量重评 + 评分惯性”，还不是跨整局持久缓存。
- 后续可加入更强的路线切换滞后阈值，避免接近同分时来回横跳。
- 后续可把 21 局、50 局级别的实战复盘统计纳入路线权重自学习。

## 8. 概率读牌与后验

当前内江 AI 的概率层，重点服务于两类场景：

- 尾盘弃牌阈值
- 碰/杠是否值得做

核心后验包括：

- `听牌后验`
  - 某家已成叫/接近成叫的概率
- `持张后验`
  - 某张还在某家手中的概率
- `牌墙后验`
  - 某张仍在牌墙中的概率

当前使用方式：

- 尾盘若点炮风险明显高于自身胡牌收益，切防守
- 补杠/明杠若显著抬高被胡概率，则降权或放弃
- 同向听下优先保留牌墙后验更高的叫口

## 9. 记分与番型约束

当前内江规则以 **5 番封顶** 为上限，结算时不允许突破。

当前结算按代码 `FanResolver._resolve_neijiang_win_fans` 执行，基础分值：

- `1 番 = 1 分`
- `2 番 = 2 分`
- `3 番 = 4 分`
- `4 番 = 8 分`
- `5 番及以上 = 16 分`

当前关键番型与分值：

- `平胡` = 1 番 = 1 分
- `卡二条` = +1 番
- `报叫` = +1 番
- `归` = 每个 +1 番；但龙七对、青龙七对中可能作为基础牌型的一部分被吸收
- `大对子` = 3 番 = 4 分
- `清一色` = 3 番 = 4 分
- `暗七对` = 3 番 = 4 分
- `龙七对` = 4 番 = 8 分；当前代码中 2 个及以上归的龙七对进入 5 番封顶档
- `清对 / 清大对` = 4 番 = 8 分
- `清七对` = 4 番 = 8 分
- `青龙七对` = 5 番 = 16 分

其他特殊名目如：

- `天和`
- `地胡`
- `海底`
- `杠上花`
- `杠上炮`
- `抢杠胡`

均应在结算页与底层记分逻辑中保持一致，并受 `5 番封顶` 约束。

七对类牌型约束：

- 七对、龙七对、清七对、青龙七对必须无副露。
- 碰、明杠、暗杠、补杠都会破坏七对类路线。
- 七对类默认不叠加卡二条。

杠分约束：

- `add_gang` 按 1 分单位结算。
- `melded_gang` 与 `an_gang` 按 2 分单位结算。
- 杠分会在结算阶段结合退税、呼叫转移、杠上炮、抢杠胡等事件重审，不等于简单即时永久入账。

## 9.5 当前牌型路线规划设计

当前 AI 已新增独立 C# `RoutePlan` 思路，用于把开局预判、中途路线切换、碰杠禁忌、番值收益统一到出牌和响应评分中。

已接入路线集合：

- `平胡 / 小屁胡`
- `卡二条平胡`
- `暗七对`
- `龙七对`
- `清七对`
- `青龙七对`
- `大对子`
- `清对 / 清大对`
- `清一色`

设计原则与当前代码口径：

- 路线是软权重，不是开局锁死。
- 路线偏好不能绕过总分排序；番型路线必须同时接受成叫速度、活张、点炮风险和查叫风险约束。
- 每次摸牌、出牌、碰杠响应前轻量重评。
- 碰、杠、报叫、进入中盘、进入尾盘属于强重评节点。
- 当前以轻量重评为主，新路线会通过分数差、向听速度、路线收益自然切换；后续可继续增加更强的跨巡目滞后阈值，避免 AI 反复横跳。
- 只要平胡能明显更快成叫，普通高番路线不能硬压速度。
- 8 分、16 分复合路线可以在前期多坚持，但中后期仍要服从成叫、查叫、防点炮。

起手与中途倾向：

- 5 对及以上：七对 / 龙七对 / 清七对主线，不碰不杠。
- 4 对：七对强副线；若顺子搭子弱可升主线，若两面搭子强则平胡主线加七对副线。
- 3 对：不默认七对，优先平胡抢听；碰牌看是否降向听或直接成叫。
- 单门 10 张及以上：清一色主线候选；若对子/刻子多，进一步评估清对；若 5 对以上，评估清七对/青龙七对。
- 单门 8-9 张：清一色副线，只能在不拖慢成叫时保留。

动作约束：

- 七对系：禁止碰、明杠、暗杠、补杠。
- 大对子：允许积极碰杠，但必须避免碰后首打同张、碰后明显变慢。
- 清对：只积极碰杠目标花色，非目标花色副露强降权。
- 清一色：优先清理非目标花色孤张，但不能为了伪清一色错过直接下叫。
- 归 / 四张同牌：默认保留为高番资源，拆掉需要综合分上有明确速度、收益或安全优势。
- 平胡：默认主路线，能下叫先下叫，宽叫和活张优先。

已接入诊断输出：

- 出牌结果输出 `routePlan.primaryRoute / secondaryRoutes / routeWeights / constraints / reasons / targetSuit`。
- 每个弃牌候选输出 `routePlanPrimary / routePlanScore`。
- Godot 内嵌 C# runtime、CLI JSON、Godot 合并层都保留路线诊断字段。
- 反应链与自行动作链在七对路线下会给碰/杠强降权，并输出“七对路线禁止碰/杠”的原因。
- 番值收益和速度损失仍由 `expectedNetScore`、`routePlanScore`、候选 `reasons` 共同解释。

## 10.5 地狱挑战专项规则

地狱挑战是独立难度，代码入口包括：

- `NeijiangHellChallengeEngine`
- `NeijiangHellChallengeReactionEngine`
- `NeijiangHellChallengeTeamPlanner`
- `NeijiangHellOracleEngine`

地狱挑战允许的信息优势：

- 三家 AI 共享 AI 手牌。
- AI 可读取本家手牌。
- AI 可读取精确牌墙。
- AI 可执行 oracle 弃牌与响应动作。

团队协作规则：

- 三家 AI 共同以本家为压制目标。
- 按分数和当前行动座位分配 `lead_suppressor / interceptor / catch_up` 等角色。
- 主压制者偏向保听、防点炮、截断本家节奏。
- 截断者偏向在不明显降速时碰/杠本家弃牌，减少本家摸牌机会。
- 追赶者在自己落后时可更积极抢听与收收益。

互动保真规则：

- 地狱挑战不能把“不给本家碰”作为绝对目标。
- 前期如果 AI 自己能下叫，可以不为了普通碰机会让路。
- 中期如果 AI 自己能下叫，且本家碰了也不下叫，可以允许本家碰。
- 后期如果本家已听，但弃牌只给碰不点炮，可以允许本家碰，以保留真实麻将体验。
- 给本家胡牌、给本家明杠加速、明显帮助本家成叫，仍应强烈规避。

地狱挑战响应规则：

- 可胡时直接胡。
- 明杠有雨钱与补牌收益，但仍需比较向听、活张与团队截断价值。
- 若同一张弃牌既可碰又可杠，C# 不能简单固定杠；但若碰后首打同张，必须判为无效副露，让明杠胜出。
- 报叫玩家仍走报叫专线，不被地狱挑战团队压制逻辑覆盖。

## 12. 测试、压测与真实评测口径

为避免把“烟测结果”误认为“真实实战能力”，当前工程统一采用以下测试分层口径。

### 12.1 C# 单点烟测

定位：只验证 C# AI 某个局部模块是否能独立计算并返回合理结果。

代表文件：

- `dotnet/AI.Core.Smoke/Program.cs`

适合验证：

- 向听 / 进张 / 自摸概率是否有基本输出
- 净分期望字段是否正常生成
- 碰、暗杠等单个反应样例是否返回预期动作

明确限制：

- 不是完整牌局
- 不代表真实胜率
- 不代表完整报叫、报杠、查叫、退税、结算链路均已走通
- 不允许仅凭烟测结果宣称 AI 已达到真实实战水平

### 12.2 Godot 回归测试

定位：验证 Godot 规则流程、状态迁移、界面桥接是否出现明显回归。

代表文件：

- `tests/NeijiangRegressionRunner.gd`

适合验证：

- 内江模式是否仍为两门 72 张
- 是否绕开定缺 / 花猪等四川麻将旧逻辑
- 报叫、报杠、查叫、退税、结算等规则是否能触发
- C# 返回结果能否被 Godot 状态机接收并执行

明确限制：

- 它是工程回归工具，不等同于玩家真实体验
- 可以跳过动画等待，但不能跳过规则状态迁移
- 若只验证局部路径，不能推导整体牌力强弱

### 12.3 AI 自动流程压测

定位：批量跑自动牌局流程，用于发现卡死、超时、状态残留、结算异常与统计趋势。

代表文件：

- `tests/ai_pressure_benchmark.gd`

当前脚本特征：

- 会实例化 `GameState.gd`
- 会将 4 家设为自动玩家
- 会尝试推进开局、出牌、反应、下一轮、结算等阶段
- 会统计 `score_changes`、`win_events`、`gang_events`、`ai_decision_metrics`
- 会输出到 `res://测试数据统计/ai压测_时间_局数_模式.json/csv`

当前必须使用的称呼：

- `自动流程压测`
- `近似牌局模拟`

当前禁止使用的称呼：

- `真实实战压测`
- `完整真人等价牌局`
- `已证明超越人类`

原因：该脚本虽然比 C# 烟测更接近完整牌局，但仍需逐项审计，确认它没有跳过关键规则、没有使用捷径决策、没有在异常状态下强行结算。审计完成前，它只能作为工程稳定性与趋势观察工具。

### 12.4 真实牌局评测标准

只有满足以下条件的测试结果，才允许纳入“真实牌局能力评估”：

- 每局从真实洗牌、发牌、庄家、牌墙开始
- 所有电脑出牌、碰、杠、胡、过均走同一条 C# 决策链
- Godot 只负责状态调度、动画与响应，不用 GDScript 兜底替 AI 做决策
- 摸牌、出牌、碰、杠、胡、报叫、报杠、查叫、退税、归、结算均按正常状态机执行
- 没有直接写入结果、没有绕过反应链、没有跳过结算链
- 每局必须自然进入 `battle_end`、流局或正常结算
- 若出现卡死、超时熔断、强制推进、残留反应队列，该局只计入稳定性问题，不计入胜率 / 净分结论
- 报告必须记录异常原因、停在哪个阶段、当前玩家、最后一张牌、待处理反应队列

### 12.5 人机实战数据闭环

当前最可信的调参来源，是玩家与 AI 在安装包中真实打一局后的实战数据。

相关代码：

- `res://autoload/GameState.gd::_update_ai_learning_after_round`
- `res://autoload/GameState.gd::_reload_ai_learning_for_new_round`
- `res://autoload/GameState.gd::_apply_ai_learning_adjustment`
- `res://scripts/core/ai_learning_engine.gd`
- `dotnet/AI.Core/Learning/NeijiangLearningEngine.cs`

相关数据：

- `user://测试数据统计/ai学习数据.json`
- `user://测试数据统计/ai参数学习历史.json`

口径要求：

- 每局正常结束后，将本局胜负、净分、胡牌、点炮、查叫、退税、碰杠收益、AI 决策摘要累加到历史数据
- 新一局开始时，AI 读取累计学习数据，调整参数面板对应权重
- 参数变化必须可追踪，不能只在内存中悄悄改变
- 自动压测未完全审计前，不允许让压测结果直接大幅改写默认参数
- 实战局数越多，学习权重可信度越高；低局数只能小幅修正

当前结论：

- C# 烟测用于确认“单点算法能算”
- Godot 回归用于确认“规则流程没坏”
- 自动流程压测用于发现“批量卡死和趋势问题”
- 人机实战数据才是当前 AI 自进化的最高优先级输入
