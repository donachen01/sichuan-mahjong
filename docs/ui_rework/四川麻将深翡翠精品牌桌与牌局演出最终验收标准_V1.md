# 四川麻将深翡翠精品牌桌与牌局演出最终验收标准 V1

状态：`实施前基线`  
适用项目：`/Volumes/AI/Codex/四川麻将工程_20260701_v2`  
设计分辨率：`2048×1152`，并覆盖 `1365×768 / 2400×1080 / 2556×1179`  
标准优先级：本文件是本轮最终视觉与交互验收标准；既有蓝桌标准仅保留为历史证据，其蓝色美术方向不再作为当前目标。既有规则、计分、触控、HUD 状态和移动端交付硬门禁继续有效。

## 1. 不可变边界

1. 不制作大厅、商业化系统或开局仪式；启动后继续直接进入牌局流程。
2. 玩家信息区允许重绘和重排内部信息，但四家外框尺寸不得小于当前基线：标准模式 `230×156 px`，紧凑模式 `196×146 px`；所有四家使用同一尺寸令牌。
3. 本家手牌不允许缩小。冻结 `HandCanvas2D` 基线：单牌正面 `132×198 px`、最大步距 `136 px`、摸牌间隔 `22 px`、胡牌张间隔 `24 px`、选中抬升 `18 px`、摸牌抬升 `8 px`。14 张牌首末外包围框、牌面字号/纹理缩放、亮度和摸牌间隔均不得因本轮美术改造下降；像素测量误差 `≤1 px`。
4. 不改变四川麻将规则、番型、计分、AI 决策或状态写入链。所有新表现层只读取 UI 快照与既有结算数据。
5. 既有美术资源在新资源完成四分辨率、回退路径和移动端验证前保留为可恢复备份；不得用删除旧资源掩盖回归。
6. 对家、上家、下家暗手继续与桌面成 `90°`，不向桌心内倾；三家牌背颜色与材质保持一致。

## 2. 独立裁判制度（逐条硬门禁）

1. 每个 `AC-*` 条目完成后，实施者先提交该条要求的客观证据，再由未参与该条实现的独立裁判员单独复核。
2. 裁判不得以实施者的口头结论、构建成功或其他条目通过替代本条证据；必须亲自读取代码/资源/测试结果，视觉条目必须亲自查看对应截图或录屏。
3. 每条裁决记录固定为：`条目ID｜evidence_paths[]｜metric_values{}｜severity_counts{P0,P1,P2}｜subjective_score{score,rubric_version}｜verdict{PASS|FAIL|PARTIAL}｜judge｜reviewed_at｜notes｜required_followups[]`。逐项验收矩阵 JSON 每项必须至少包含上述字段；`status` 仅表示流程状态，不替代 `verdict`。只有 `verdict=PASS` 且 `P0=0` 且 `P1=0` 时，`status` 才允许写为 `已验证`。
4. 单条通过条件：本条全部硬指标满足、主观评分 `≥4/5`、`P0=0`、`P1=0`。任何一项失败即该条 `FAIL`；不得用总分或其他条目得分抵消。主观评分统一解释：`5=可直接发布，无明显违和`；`4=仅有轻微非阻塞瑕疵`；`3=可用但存在明显违和或可读性问题`；`2=影响理解、阅读或操作`；`1=不可接受`。凡主观评分 `<5`，裁判必须附至少两句文字依据和一个对应截图区域。
5. `FAIL` 条目必须回到实施阶段，补证据后由同一裁判或另一名独立裁判重新完整评判；只有最后一次明确 `PASS` 才能标记 `已验证`。
6. 裁判报告统一存入 `evidence/ui_emerald_final_<日期>/judges/AC-*.md`；截图、录屏、测量 JSON 和测试日志存放在同批证据目录中。
7. 项目总放行条件：本文所有 `AC-*` 均为 `PASS`，同时既有规则/计分回归无失败，Android 与 iOS 交付达到第 14 节所述证据层级。

### AC-VIS-01 颜色令牌落地

- 所有主桌、玩家框、动作、定缺与结算组件从同一主题脚本读取上述令牌；不得在组件中继续散落旧蓝桌主色。

### AC-VIS-02 明暗层级与克制高光

- 桌面中央相对主体只亮 `3%–5%`；边缘相对主体压暗 `5%–8%`，过渡连续无色带。
- 旧铜只用于细边、嵌线和焦点，不得覆盖大面积面板；任何常驻高光不得抢过麻将牌白面。
- 证据：线性亮度取样、截图直方图、裁判视觉复核。

### AC-TYPE-01 字体资产与回退

- 所有关键中文 Label 明确绑定内置字体；iOS 字体回归 Runner 无缺字、方框、错误回退。
- 姓名、分数、定缺、动作、结算标题和明细分别达到上表下限；不得通过减小字号解决布局问题。
- 证据：主题/场景资源审计、中文字符截图、iOS 字体 Runner。

### AC-TYPE-02 可读性与对比度

- 关键文字对背景对比度 `≥4.5:1`；大号文字 `≥3:1`。描边只辅助复杂背景，不得形成粗黑廉价字效。
- 正负分必须同时使用颜色与 `+/-`；定缺、庄家、当前回合、已胡均包含文字或明确图形，不以颜色单独传意。
- 证据：对比度测量表与状态矩阵截图。

## 5. Blender/PBR 桌体与纹理

### AC-ART-01 Blender 可复现资产链

- 使用 Blender `5.2 LTS` 的项目脚本确定性生成桌体、中央方向器和正交 UI 外壳；脚本、源参数、导出路径和生成命令纳入仓库。
- Blender 只生产三维资产和离线 UI 外壳；动态文字、数据、触控与布局继续由 Godot Control 管理。
- 证据：生成脚本、Blender 日志、GLB/PNG 哈希及重新生成一致性记录。

### AC-ART-02 实体桌体建模

- 桌体必须具备厚桌框、内外双倒角、墨黑绿皮革包边、可见但克制的缝线、下沉旧铜嵌线、软硬材质过渡和连续圆角；不再由数个无细节圆角盒代替。
- 桌体目标 `20k–30k` 三角面，中央方向器 `5k–8k` 三角面；桌体材质槽 `2–3` 个，不得逐物件制造大量重复材质。
- 四分辨率不得出现破面、穿插、透明洞、桌布超出框体或黑柱。
- 证据：Blender 统计、GLB 检查、四分辨率截图。

### AC-ART-03 短绒毛毡 PBR

- BaseColor/Normal/ORM 均为 `2048²`；运行时桌布 metallic=`0`，roughness 基线 `0.78–0.90`，局部变化不超过 `±0.03`。
- 中尺度顺逆毛方向变化 `2%–4%`；微纤维主要进入 normal/roughness，不得在 BaseColor 中出现明显白线、网格、正弦条纹或摩尔纹。
- 48×48 空桌面区域单通道标准差 `≤8`，但不得完全纯色；四分辨率视觉裁判不得发现明显重复接缝。
- 证据：纹理尺寸/通道审计、材质参数、局部像素统计和 200% 放大图。

### AC-ART-04 蜀锦边缘暗纹

- 蜀锦纹样只允许位于桌面外圈 `8%–10%` 范围，中央出牌区保持干净；纹样与底色相对亮度差 `2%–3%`。
- 不显示任何麻将平台文字、品牌 Logo 或水印；不得使用高频菱格、回纹、云纹铺满桌面。
- 证据：暗纹遮罩图、边缘/中央像素差和全桌截图。

### AC-ART-05 皮革、黑胡桃与旧铜

- 皮革围边使用 `1024²` 或 `2048²` atlas，具备细微皮纹、缝线和高粗糙度；黑胡桃只保留低对比木纹；旧铜 metallic `0.35–0.65`、roughness `0.35–0.55`。
- 三种材质在常规镜头下可凭明暗/粗糙度区分，但不得产生镜面强闪和塑料感。
- 证据：材质参数、近景渲染和主镜头截图。

### AC-ART-06 Godot 保留 PBR 材质

- `SichuanTableStage3D` 加载新 GLB 后必须保留/正确映射 Blender PBR 材质，不得再用单色 StandardMaterial 或运行时平涂覆盖整套材质。
- 旧桌体只作为显式 fallback；主路径与 fallback 路径均能加载，主路径失败必须可诊断。
- 证据：源码审计、运行时材质合同、主路径与 fallback Runner。

## 6. 玩家信息区（外框不缩小）

### AC-HUD-01 面板尺寸硬锁

- 四家面板标准模式均不小于 `230×156 px`、紧凑模式均不小于 `196×146 px`，外框位置不侵入手牌、牌河和安全区。
- 重绘前后四家面板外框宽高不得减少；动画期间外框 rect 误差 `≤1 px`。
- 证据：四分辨率 rect JSON、前后对比图、布局 Runner。

### AC-HUD-02 面板材质与内部层级

- 面板为墨玉/黑漆九宫格外壳：低对比蜀锦底、1–2 px 旧铜细边、切角轮廓；不得回到蓝灰矩形卡片。
- 固定内部信息：头像/座位徽章、玩家名、总分、角落庄家标记、底部内嵌定缺；分数优先级高于装饰。
- 证据：四家正常状态截图、九宫格资源及节点层级审计。

### AC-HUD-03 当前、已胡与得分状态

- 当前玩家：边缘亮起时长 `180 ms`，随后仅弱呼吸，不移动、不缩放面板；reduced-motion 下为稳定高亮。
- 已胡玩家：整体饱和度下降并显示“已胡”印章，姓名和分数仍清晰。
- 分数变化先在面板附近显示增减，再短暂高亮总分；不得改变面板大小和位置。
- 证据：正常/当前/已胡/加分/减分录屏及 reduced-motion 对照。

## 7. 手牌与牌张反馈（完全保留尺寸）

### AC-HAND-01 手牌几何与亮度硬锁

- 第 1 节冻结的全部手牌数值保持不变；14 张手牌首末包围框与基线误差 `≤1 px`。
- 本家牌面白度保持与弃牌白面一致：同场景中位亮度差 `≤3/255`；不得降低字面清晰度或总手牌宽度。
- 证据：基线/新版布局 JSON、像素亮度统计、2048×1152 对比图。

### AC-HAND-02 摸牌、选牌与手型

- 摸牌从墙到手牌最右端 `180–220 ms`，落位缓冲 `40–60 ms`；摸牌间隔保持 `22 px`。
- 选牌继续抬升 `18 px`，暖象牙/旧铜手型在 `120–160 ms` 内淡入；不得缩放麻将牌或增加大块背板。
- 摸牌标记与选牌手型是不同形状；reduced-motion 下停掉旋转/循环但状态仍可识别。
- 证据：逐帧录屏、布局测量、正常/减弱动态截图。

### AC-HAND-03 出牌与牌河落位

- 出牌从手牌移动到固定牌河格 `180–240 ms`，有轻微落地但无屏幕震动；其他手牌只在落地后收拢。
- 绿色旋转菱形仅在最新弃牌落位后出现在牌正上方；不挪动牌河、不遮住牌面。
- 证据：逐帧录屏、事件顺序日志、牌河稳定性 Runner。

### AC-HAND-04 自摸展示合同

- 本家自摸必须保持整手正面平扣可见，不得拆出单独胡牌节点，并且仅在真实 `winning_tile_id` 上保留 `1` 个自摸标记；其他家自摸继续整手平扣并统一显示翡翠牌背。
- 杠上花必须先显示补牌落位，再出现“胡”选择；补牌保留摸牌间隔。不得因演出丢失可胡按钮。
- 证据：本家普通自摸、本家杠上花、三家各自摸的状态截图与交互 Runner。

### AC-HAND-05 碰杠来源箭头

- 来源箭头统一为小号蓝色卡通箭头 `SOURCE_ARROW_BLUE`，位于副露中心上方：碰指向三张中的第 `2` 张，杠指向四张中的第 `2` 张。
- 箭头不得大到覆盖牌面；同时以朝向/来源座位数据表达来源，不能只靠蓝色。
- 证据：四个来源座位、碰/直杠/补杠/暗杠状态矩阵截图与位置测量。

## 8. 空间布局与中央区域

### AC-LAYOUT-01 中央轻量方向器

- 移除常驻的大号中央信息框，改为小型四向 3D 方向器：当前方向点亮，中央显示倒计时；余牌使用相邻的小型翡翠数字牌。
- 不常驻显示“本家出牌中”等长句；回合文字只作短时辅助，且方向仍有文字/形状，不以颜色单独表达。
- 中央方向器目标不超过当前 `210×210 px` 占位，且其可见实体面积 `≤` 旧大框可见面积的 `55%`。
- 证据：清洁桌面截图、旧新面积比例测量 JSON 与四方向状态截图。

### AC-LAYOUT-02 中央净空与牌河

- 中央区域为神圣净空：四家牌河采用固定原点和固定网格，任何压力状态均不与中央方向器、其他牌河或手牌相交。
- 最新牌标记不得改变牌河布局；被碰/杠移除的弃牌不得导致剩余弃牌整体跳位或重排。
- 证据：每家 18 张压力场景、移除前后坐标差、牌河 Runner。

### AC-LAYOUT-03 副露导轨

- 四家副露贴近各自桌边导轨；每家最多 4 组时不得与手牌、牌河、玩家面板或安全区重叠。
- 副露阅读方向与玩家方位一致；对家、上家、下家牌姿继续与桌面 `90°`。
- 证据：四家 4 组压力截图与碰撞 rect JSON。

### AC-LAYOUT-04 情境动作区

- 动作区位于本家手牌右上方安全区域，只展示当前可执行动作，顺序固定为 `胡、杠、碰、过/取消`；“胡”层级最强。
- 视觉壳可比现版更精炼，但真实触控矩形不得缩小：胡 `≥132×132 px`，其他动作 `≥108×108 px`，各触控矩形不重叠且不压住手牌。
- 证据：1/2/3/4 个动作状态截图、触控 rect 和 TouchTarget Runner。

## 9. 定缺界面

### AC-DQ-01 只展示三个选择

- 定缺阶段只显示 `条、筒、万` 三枚按钮；不显示大标题、解释文字、大面积提示框或额外开局步骤，不遮挡本家手牌。
- 每枚按钮维持现有高可点面积，视觉/触控不小于 `230×230 px`；布局在四分辨率及 iPhone 安全区内完整。
- 证据：四分辨率定缺截图、触控矩形，以及更新后的 TouchTarget Runner。Runner 必须断言每枚按钮 rect `≥230×230 px`；在 Runner 更新前，本条不得仅凭 Runner PASS 判定通过。

### AC-DQ-02 翡翠印章交互

- 按钮采用 Blender 正交烘焙的翡翠印章外壳；桌面仅压暗 `10%–15%`。
- 选中项抬升 `8–12 px` 并短暂描边发光，其他两项降低饱和度；推荐仅用小火苗/小标签，不增加大说明。
- 提交沿用当前确认合同，不添加步骤；动画结束后所有 transform 必须复位，reduced-motion 使用静态状态切换。
- 证据：默认/推荐/选中/提交/减弱动态录屏与状态 Runner。

## 10. 牌局演出架构与事件唯一性

### AC-PRES-01 只读表现导演

- 新表现层按职责分离为 `TablePresentationDirector`、`TileMotionLayer`、`CalloutFxLayer`、`ScoreDeltaLayer`、`TurnIndicatorLayer`、`ResultTransitionLayer` 或等价模块。
- 数据流只能是 `GameState/UI snapshot → 表现层`；表现模块不得写规则、计分或 AI 状态。
- 证据：依赖图、源码审计、无写入合同测试。

### AC-PRES-02 事件签名与只播放一次

- 至少支持并持久去重下列签名：`discard:round:turn:seat:tile_id`、`peng:round:seat:source_seat:tile_id`、`gang:round:seat:gang_type:tile_id`、`win:round:winner:source:winning_tile`、`score:round:event_index:seat:delta`。
- 同一快照重复刷新 `20` 次，每个事件仍只播放一次；新局必须安全清空旧签名。
- 证据：事件日志和 `20/20` 去重 Runner。

### AC-PRES-03 优先级与不可中断动作

- 优先级固定：`胡/抢杠胡/杠上花 > 杠 > 碰 > 出牌 > 摸牌 > 分数 > 普通提示`。
- 高优先级只可中断低优先级装饰，不得中断关键牌张位移或造成牌张瞬移/消失；队列清理后节点状态稳定。
- 证据：冲突事件 Runner 与逐帧录屏。

## 11. 动画节奏与事件表现

### AC-MOTION-01 时间与运动总合同

| 动作 | 时长 |
| --- | ---: |
| 动作按钮入场 | `150–200 ms` |
| 摸牌 | `180–220 ms` |
| 出牌 | `180–240 ms` |
| 碰牌飞入 | `180–240 ms` |
| 杠牌组成 | `220–280 ms` |
| 事件字入场 | `160–220 ms` |
| 事件字停留 | `300–450 ms` |
| 分数飘字 | `350–500 ms` |
| 当前玩家亮边 | `160–180 ms` |

- 所有 HUD 动效禁止屏幕震动；视觉层动画不得改变真实触控 rect、布局 rect 或 tile_id 映射。
- 证据：动画合同字典、逐帧计时与 Motion Runner。

### AC-MOTION-02 碰、直杠、补杠与暗杠

- 碰：来源弃牌飞入副露，三张落位后显示“碰”。
- 直杠：来源牌飞入、四张组成后显示“杠”，同时出现点杠者与开杠者分数变化。
- 补杠：第四张从手牌进入已有碰牌，显示“补杠”，三家付款与开杠者收分分别出现。
- 暗杠：四张按本轮新合同展示——边上两张正面、中间两张牌背；显示“暗杠”，三家付款与开杠者收分分别出现。自本条生效起，旧 3D 合同 `four_distinct_face_down_jade_tiles` 明确作废，不得作为本轮门禁依据；对应 Runner 必须更新为新合同后，本条才允许 PASS。
- 证据：四类录屏、最终牌姿截图与分数事件日志。

### AC-MOTION-03 胡牌事件

- 自摸：胡牌张微光/玩家框高亮，显示“自摸”与番数，三家付款和赢家总收分可见。
- 杠上花：补牌先落位，随后显示“杠上花”；杠钱与胡牌钱作为两个独立分数事件呈现。
- 点炮：弃牌移动到赢家区域后显示“胡”，放炮者与赢家分数变化可见。
- 抢杠胡：补杠牌转移给赢家后显示“抢杠胡”，入场线条可更锐利但不得震屏。
- 证据：四类录屏、事件顺序和结算数据对照。

### AC-MOTION-04 事件字美术

- 事件字采用原创 2D 透明 PNG/SpriteSheet，由概念图二次重绘后导入 Godot；不得复制参考游戏资源。
- “碰”=翡翠印章+青绿色微光；“杠”=深青玉+旧铜；“胡”=朱砂印+少量金粒；“自摸”=暖象牙字+翡翠环；“杠上花”=朱砂+极少淡金花瓣且不遮胡牌张；“抢杠胡”=锐利入场线、无震屏。
- 事件字在 1365×768 下仍清晰，且不遮关键牌、动作按钮或分数。
- 证据：透明图集、源 PSD/Krita/Blender 工程、分层导出记录、作者自制声明、参考图清单与差异说明、六类静帧与录屏。仅凭 PNG/录屏不得判定原创。图像生成工具只允许用于概念探索，最终资源必须经过人工二次设计与分层重绘。

### AC-MOTION-05 减弱动态

- `accessibility/reduced_motion=true` 时移除非必要路径位移、循环、旋转和粒子，仅保留淡入、落位和数值更新；所有活动 Tween 被停止并复位。
- 切换前后牌位、HUD rect、触控 rect 和事件最终状态一致；无残留 Tween/幽灵节点。
- 证据：开关前后状态 JSON 与 reduced-motion Runner。

## 12. 结算页统一

### AC-SETTLE-01 视觉统一且保留明细

- 结算页使用深翡翠/墨玉/旧铜主题和 Blender 九宫格面板，不再使用与主桌冲突的蓝灰配色。
- 获胜行使用更强翡翠高亮；分数列是第一视觉焦点；所有原有明细、番型、对象和逐项得分均保留，可审计。
- 证据：四家结算截图、九宫格资源与明细节点审计。

### AC-SETTLE-02 数据权威与账本一致

- 结算 UI 只显示 `settlement_data/score_changes`，不得自行重算或额外加自摸 `+1`。
- 每位玩家顶部/左侧最终收分严格等于本局明细有符号合计；四家本局净变化总和为 `0`（规则允许的独立账项也必须完整入明细）。
- 证据：自摸、点炮、杠上花、抢杠胡、流局五类账本测试。

### AC-SETTLE-03 转场节奏

- 胡牌后先保留桌内胜利与分数演出约 `1.0 s`，然后正常打开详细结算；不得瞬间跳页，也不得为了动画隐藏明细。
- reduced-motion 下允许缩短装饰，但事件终态与账本内容完全相同。
- 证据：正常/减弱动态转场录屏与时间测量。

## 13. 触控、适配、性能与回归

### AC-ENG-01 触控硬门禁

- 本家每张牌真实投影点击矩形最小边 `≥44 pt`；工具栏和退出按钮 `≥76×76 px`；定缺与动作按钮使用各自更强门槛。

- 证据：TouchTarget、实时点击和去重 Runner。

### AC-ENG-02 四分辨率与安全区

- `1365×768 / 2048×1152 / 2400×1080 / 2556×1179` 的定缺、牌局、动作、明牌、自摸、副露压力和结算矩阵无裁切、重叠、黑柱或安全区侵入。
- 玩家面板与手牌不缩小；空间不足必须优先压缩中央装饰、空隙或非关键说明。
- 证据：完整截图矩阵及自动 rect 碰撞报告。

### AC-ENG-03 移动渲染性能

- 性能门禁分为静态合同与参考机合同。静态合同：沿用 Forward+，实时灯 `≤2`、投影灯 `≤1`、RigidBody=`0`，不逐牌创建灯或唯一材质。
- 参考机固定为本项目当前开发机：`MacBookPro18,3 / Apple M1 Pro 10-core / 16 GB / macOS 26.4.1 (25E253)`。使用 Release 构建，冷启动后预热 `60 s`，低电量模式关闭、屏幕亮度 `50%`、飞行模式开启，运行固定压力场景 `600` 帧；使用 Godot Performance Monitor 与平台原生工具同步采集。门槛：平均 FPS `≥55`、1% low `≥45`、峰值 RSS `≤1.2 GB`。
- 证据：性能 CSV/JSON、采集命令、环境快照、运行日志与资源实例统计。未在指定参考机和上述条件采集时，本条状态只能为 `已修未验`，不得 PASS。

### AC-ENG-04 规则与历史功能无回归

- 表现层改动不得改变规则结果、可操作集合或最终分数。验证项目按本次改动风险选择并逐项记录；除非用户明确指定，不创建、扩充、维护或默认执行固定回归清单，也不以脚本、CI 或其他文档变相重建。
- 现有单项 Runner 保持独立可用，只在与当前修改直接相关时按需执行；历史报告中的既有结果保持不变。
- 证据：全量 Runner 汇总、固定种子前后快照 diff、C# Release 构建。
