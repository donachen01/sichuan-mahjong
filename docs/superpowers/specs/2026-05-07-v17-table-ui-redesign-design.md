## 1. 目标

本次任务目标分两步：

1. 先把用户提供的原 V17 精修图修正为最终目标模板图。最终模板必须完整保留原 V17 精修图的面板大小、区域布局、区域尺寸、牌局内容和信息密度，同时把视觉风格、背景质感、桌布光影、面板材质、麻将牌厚度、玩家卡片和按钮语言改成用户提供的新风格参考图效果。
2. 用户确认最终目标模板图后，再将现有 Godot 牌桌核心游戏界面按该模板落地。

本次不是简单换色、加圆角、加阴影，也不是继续小修小补现有界面。最终产物必须在截图对照时明显接近最终目标模板图的布局比例、色调、材质、麻将牌尺寸、信息密度和 3D 卡通质感。

本规格定义两个参考源：

- 布局参考图：用户提供的原 V17 精修图，也就是此前的目标图。它负责面板大小、区域布局、区域尺寸、牌数量、牌位置、玩家信息内容和整体信息密度。
- 风格参考图：用户新提供的绿色牌桌参考图。它负责背景、桌布质感、光照、凹槽式面板、麻将牌厚度、玩家卡片质感、按钮和角标质感。

最终目标模板图 = 布局参考图的结构与内容 + 风格参考图的视觉语言。Godot 工程只在最终目标模板图确认后开始实现。

本规格参考项目内已有文档：

- `docs/ui_baseline/UI_BASELINE.md`
- `docs/ui_baseline/TABLE_LAYOUT_BASELINE.md`
- `docs/ui_baseline/neijiang-mahjong-ui/SKILL.md`

## 3. 非目标

本次不以“代码有变化”为成功标准，不以“比当前运行图稍好看”为成功标准，也不以单纯 Godot `StyleBoxFlat` 调色为主要手段。

以下结果视为失败：

- 仍然是大面积扁平浅绿面板。
- 中心桌面仍然像一块大空白 UI 面板。
- 麻将牌只是白色圆角矩形，没有明显侧厚、倒角、接触阴影。
- 左右和顶部仍然有大量空白，整体不贴近布局参考图的信息密度。
- 牌桌、按钮、头像框、牌面之间材质语言不统一。
- 出牌/手牌/碰杠牌的位置明显偏离布局参考图坐标。
- 在最终模板确认前直接修改 Godot 游戏工程。
- 在本轮提前加入顶部或左右木质桌沿。

## 4. 设计原则

### 4.1 视觉方向

采用“高质感绿色牌桌 + 精致卡通 3D 牌局组件”方向：

- 保留布局参考图的所有区域大小、位置和内容。
- 背景与桌布吸收风格参考图的深绿渐变、中心光照、绒布质感和空间感。
- 原 V17 浅色板块改为嵌入牌桌的凹槽/压线/柔光面板，不再像独立白板拼接。
- 暖金描边和柔光作为层级分隔，但不喧宾夺主。
- 鲜亮但不刺眼的绿色牌背作为视觉记忆点。
- 麻将牌采用象牙白正面、绿色侧边、圆润倒角、柔和接触阴影。
- 玩家卡、按钮、胡牌槽采用风格参考图那类深绿半透明、高光、浮雕厚面板，而不是扁平后台卡片。
- 顶部和左右木质桌沿暂不加入最终模板第一版，待内部牌桌风格接近后再单独评估。

### 4.2 `frontend-design` 使用方式

`frontend-design` 在本任务中用于前置定义视觉系统，而不是后置修补代码：

- 先锁定构图和视觉语言。
- 先制作最终目标模板图。
- 先评审目标模板图，不直接改游戏工程。
- 再拆分组件系统和资产清单。
- 再落实到 Godot 控件、纹理和脚本。
- 每次实现后用截图和最终目标模板图对照验收。

### 4.3 资产驱动原则

项目本地 UI skill 已明确指出：目标质量不能依赖代码样式微调达成。本轮必须采用资产驱动方式。

实现时应优先使用：

- `TextureRect`
- `NinePatchRect`
- `TextureButton`
- texture-backed `Button` stylebox
- 程序生成的 2.5D tile texture
- 可复用的 panel/button/avatar/tile 资源

`StyleBoxFlat` 只允许作为占位或透明交互层，不应承担最终主视觉。

## 8. 麻将牌视觉规格

### 8.1 我方手牌

在 `2048 x 1152` 基准下：

- 目标牌面尺寸：`104 x 156` 到 `108 x 162`
- 单牌触控区域：不小于牌面实际尺寸
- 14 张牌全部可见
- 最后一张摸牌与前 13 张有明显间隔
- 牌面字形必须清晰，不糊、不挤、不被阴影污染

### 8.2 公共出牌

- 对家/我方公共出牌：约为我方手牌 `58% - 68%`
- 上家/下家横置公共出牌：宽高按方向旋转后保持可读
- 最近出牌可有轻微高亮，但不应破坏目标图整体克制感

### 8.3 对手手牌背

目标图中绿色牌背是强记忆点，本轮必须实现：

- 鲜亮绿牌背
- 圆角厚牌
- 侧边厚度
- 接触阴影
- 牌背可重复堆叠排列

### 8.4 3D 厚度

每张牌至少有 5 层视觉：

1. 接触阴影
2. 绿色/浅灰侧边
3. 正面象牙白牌体
4. 内部轻微高光
5. 图案/文字层

这 5 层可以用生成贴图、NinePatch、程序绘制或组合控件实现，但最终截图必须肉眼可见。

## 10. 组件系统

### 10.1 牌桌背景组件

职责：

- 绘制全屏深翡翠桌布。
- 绘制中心主牌局区的深绿绒布。
- 绘制中心牌桌外侧轻微木框或暗金边框。

不负责：

- 麻将牌逻辑
- 出牌排序
- 玩家状态

### 10.2 十字公共出牌板组件

职责：

- 生成五块浅青绿/奶油绿出牌底板。
- 控制五块板之间的十字结构和边界。
- 为四家公共弃牌提供容器坐标。

要求：

- 顶、底、左、右、中心必须分块明确。
- 分块间不能像一整块大白板。
- 底板色调必须接近目标图，而不是当前图 1 的灰绿面板。

### 10.3 MahjongTile 视觉组件

职责：

- 统一绘制正面、背面、横置、竖置、小牌、大牌。
- 支持程序生成或贴图驱动。
- 支持选中、摸牌、最近出牌、推荐/危险标记。

要求：

- 所有牌共享同一套厚度和光影语言。
- 大小缩放不能导致边框和阴影比例失衡。
- 牌面图案不能失真。

### 10.4 玩家信息卡组件

职责：

- 显示头像、昵称、分数、庄标、定缺标。
- 保持四家位置贴边。
- 后续可替换为 3D 动物头像。

目标图要点：

- 头像是卡通 3D 角色感，不是文字标签。
- 信息卡小而清楚，不能抢中心牌局。
- 分数足够大。

本轮最低要求：

- 头像框风格与目标图接近。
- 若没有最终头像素材，必须预留头像资源接口，不把文字头像当最终方案。

### 10.5 动态牌区组件

职责：

- 对四家手牌、碰杠、胡牌张做独立板块布局。
- 处理动态伸缩。
- 避免重叠。

要求：

- 顶部、底部必须是“碰杠区 + 手牌区 + 胡牌槽”三段。
- 左右必须是“碰杠列 + 手牌列 + 胡牌槽”三段。
- 胡牌槽使用独立橙色/暖色单槽。

### 10.6 操作按钮组件

职责：

- 显示胡、碰、杠、过、定缺、下一局等操作。
- 保持触控面积。
- 不遮挡手牌。

视觉要求：

- 主按钮 `胡`：直径或等效面积约 `136-156`
- 次按钮：约 `112-132`
- 3D 圆润浮雕/果冻感
- 高光、暗部和接触阴影清楚

## 14. 验收标准

### 14.1 截图验收

每轮完成后必须生成至少一张 `2048 x 1152` 主牌桌截图，并与最终目标模板图对照。

必要截图：

- `table_normal_2048x1152.png`
- `table_reaction_buttons_2048x1152.png`
- `table_normal_1365x768.png`

如截图工具不能固定分辨率，必须说明限制并提供当前可用分辨率截图。

### 14.2 布局验收

通过条件：

- 主要区域位置与本规格坐标一致，视觉误差约 `±3%`。
- 顶部、左右、底部动态牌区贴近布局参考图边缘信息密度。
- 中心区域是明确五块十字结构。
- 底部我方动态牌区三段分明。
- 顶部对家动态牌区不下坠。
- 左右动态牌区不侵入顶部动态区。

### 14.3 色彩验收

通过条件：

- 整体第一眼接近最终目标模板图的深绿牌桌 + 凹槽面板 + 厚麻将牌体系。
- 不再出现大面积灰绿白板。
- 麻将牌背有鲜亮绿色。
- 胡牌槽/按钮有暖橙色点缀。

### 14.4 3D 质感验收

通过条件：

- 麻将牌有明显厚度、倒角、高光、接触阴影。
- 面板有 NinePatch 或等效贴图材质，不是纯 StyleBoxFlat。
- 按钮有浮雕/果冻感。
- 玩家卡片有材质和层级，而不是薄线框。

### 14.5 功能验收

通过条件：

- 出牌选择仍可点击。
- 最后一张摸牌仍有间隔。
- 碰、杠、胡、过按钮仍能按原逻辑显示和触发。
- 定缺流程不受影响。
- 下一局按钮不受影响。
- AI 辅助入口不丢失，但可收进二级菜单。

### 14.6 APK 验收

最终实现通过后必须导出：

- `build/android/NeijiangMahjong-release.apk`

并记录：

- 导出时间
- APK 大小
- Godot 导出结果
- 已知警告

## 15. 风险与应对

### 15.1 最大风险：只靠代码样式无法达到最终模板图

应对：

- 明确使用方案 B。
- 先做最终目标模板图和资产样张。
- 主视觉组件使用贴图/NinePatch。

### 15.2 风险：最终模板图是理想效果，实际游戏状态动态更多

应对：

- 保留现有游戏逻辑。
- 以动态容器承载牌数量变化。
- 验收时覆盖 14 张手牌、碰杠、胡牌张、反应按钮等状态。

### 15.3 风险：分辨率适配导致边缘裁切

应对：

- 固定 `2048 x 1152` 基准。
- 加入 `1365 x 768` 验收截图。
- 较小分辨率只压缩间距，不压缩触控区域到不可用。

### 15.4 风险：资产生成风格不稳定

应对：

- 先出最终目标模板图和组件样张。
- 用户确认后再拆分资产。
- 资产命名和路径固定。
